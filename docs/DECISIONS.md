## 1. Decisions

### D-01 Frontend architecture
**Context.** Heed is a Chrome MV3 extension (React, TypeScript, Vite). MV3 service workers are ephemeral; the extension must show data instantly, keep reminding while offline, and must never hold secrets.

**Decision.**
- Surfaces: popup (Today), side panel (Upcoming, Review, history, Why), options page (connections, privacy and data, settings), and a service worker. No content scripts and no Gmail DOM access.
- **Local-first with a single writer.** The service worker owns networking, the outbox, alarms, and notifications; UI pages read the `chrome.storage.local` cache and send commands via messaging. State is rehydrated from storage on every worker wake (no in-memory assumptions).
- Offline: optimistic mutations through an idempotent outbox (UUID idempotency keys, `If-Match` versions); delta sync via a per-user change-sequence cursor.
- Stack: React 18, TypeScript strict, Vite multi-entry build with a typed manifest generator (plain Vite, not CRXJS, to avoid depending on a build plugin with uncertain maintenance; WXT was considered and is the fallback if build config grows past roughly 100 lines), Tailwind CSS (build-time) and Radix primitives for accessibility, React Router (hash) in side panel and options, Zod DTOs shared with the server through `packages/shared`.
- Permissions are minimal: `identity`, `storage`, `alarms`, `notifications`, `sidePanel`; host permission for the API origin only.

**Alternatives rejected.** Content script injected into Gmail (fragile against DOM changes, broad host permissions, harder Web Store review, privacy-hostile). Web app plus thin extension shell (more surface, loses native notifications and badge). In-extension AI/Gmail processing (would need Google tokens in the extension, which violates the core constraint). Redux or TanStack Query in the extension (unneeded; the worker owns fetching).

**Consequences.** Slightly more plumbing (messaging layer, outbox) than a naive extension; in return deterministic offline behavior and a clean security boundary. *(Amended in Stage 0, D-24: the extension also contains no scheduling, relevance, quiet-hours, cap, or text-composition logic; it displays server-composed notifications and acknowledges them.)* Side panel requires a recent Chromium; unsupported browsers degrade to popup-only.

### D-02 Backend architecture
**Context.** Single developer, about 10 users, zero-cost target, TypeScript throughout, needs OAuth, sync, jobs, and an AI pipeline.

**Decision.** A **modular monolith** on Node.js (current Active LTS, pinned) with **Fastify**, Zod validation (type-provider), Prisma, pino, Vitest. Modules: `auth`, `integrations`, `sync`, `detection`, `tasks`, `events`, `reminders`, `privacy`, `internal` with enforced boundaries (services only; routes are thin). Pure logic lives in `packages/detection` and `packages/ai` with no I/O so it is exhaustively unit-testable. A Postgres-backed job table with `FOR UPDATE SKIP LOCKED` leases provides background work; there is no separate queue or worker service.

**Alternatives rejected.** NestJS (heavier DI/boilerplate than needed at this size). Express (no first-class schema validation or typing). Hono (excellent, but ecosystem and Prisma/Node ergonomics are better with Fastify here). Microservices (operational cost with no benefit at ten users). Redis/BullMQ (extra paid or limited free infrastructure; Postgres is sufficient). Serverless functions per route (cold starts per function, harder local dev and testing).

**Consequences.** One deployable unit and one DB; scale-out needs care with in-memory rate limits (accepted). The architecture keeps the seams (job interface, provider interfaces, module services) that allow extracting a worker later (D-14).

### D-03 Database choice
**Context.** Relational data with strong consistency needs (task state machine, change-sequence sync, deletion guarantees), Prisma required, free tier required.

**Decision.** **PostgreSQL on Neon (free plan)**, accessed via Prisma with the pooled endpoint at runtime and the direct endpoint for migrations. Use only portable Postgres features so the provider can be swapped (Supabase free Postgres is the documented fallback; the schema, migrations, and queries are plain Postgres). Verified free-plan facts: 100 CU-hours/month per project, 0.5 GB storage, compute autosuspends after 5 idle minutes, 6-hour restore window (1 GB cap), 10 branches. Branches serve as `staging` and ephemeral test databases.

**Design consequence for compute hours.** A 5-minute tick would keep compute permanently awake (about 180 CU-hours/month at 0.25 CU) and exhaust the quota; a **15-minute tick** lets it suspend between runs (roughly 35% duty, about 65 CU-hours). This is measured in Phase 0 and monitored afterwards; if the quota is at risk, reduce tick frequency to 30 minutes or move to Supabase.

**Alternatives rejected.** Supabase free (viable fallback: always-on compute, but projects pause after a week of inactivity and its bundled auth/storage would tempt lock-in). SQLite/Turso (not what was specified; weaker fit for Prisma migrations and concurrent job claiming). Firestore (not relational, weak for sync-sequence and deletion semantics). Self-hosted Postgres on a free VM (operational burden and security risk).

**Consequences.** Cold DB wake-ups add about 1 s to the first query; 6-hour recovery window means we do **not** rely on provider backups (derived data is reconstructible from Gmail/Calendar, and users are told). Prisma client size and cold start on Cloud Run must be measured; the spike evaluates the Rust-free client with a driver adapter if available.

### D-04 Authentication architecture
**Context.** The extension cannot hold secrets; Gmail/Calendar need offline access (refresh tokens); users must be able to connect and disconnect each integration separately.

**Decision.**
- **Server-side OAuth 2.0 authorization-code flow with PKCE** using a Google **Web application** client. The extension opens `launchWebAuthFlow` to the Heed API's `/v1/auth/google/start`; the API redirects to Google, handles the callback, exchanges the code with the client secret, verifies the ID token, stores the refresh token **encrypted**, then returns a **single-use, 60-second, PKCE-bound `heed_code`** to the extension's `chromiumapp.org` redirect. The extension exchanges it (with its code verifier) for a **Heed session token**.
- Redirect URI validation is an exact allowlist of extension IDs. Dev and staging extension builds pin the ID via the manifest `key`; production uses the Web Store ID.
- **Separate consent flows per integration** (identity, Calendar, Gmail) with least scopes (`openid email profile`, `calendar.events.readonly`, `gmail.readonly`) and no `include_granted_scopes`, so each can be revoked independently (to be verified; unresolved #3). Connecting requires a connect-ticket bound to the signed-in user, and the callback must return the same Google `sub` (account-mismatch protection).
- **Heed session:** opaque 256-bit token, only its SHA-256 stored, 30-day sliding idle and 90-day absolute expiry, revocable per device.
- Google OAuth publishing status: **In production (unverified)**, because Testing mode expires refresh tokens after 7 days (verified) and caps test users at 100. The unverified app warning and the 100-user cap are accepted for the beta; a server-side email allowlist (`BETA_ALLOWED_EMAILS`) enforces the cap far below 100.

**Alternatives rejected.** `chrome.identity.getAuthToken` (puts Google access tokens in the extension and cannot do offline refresh). Public-client PKCE entirely in the extension (refresh token would live in the extension). Firebase/Supabase Auth (adds a vendor and still needs Google provider tokens server-side). Cookie sessions with a hosted web app (more surface, CSRF concerns, no benefit for an extension).

**Consequences.** One long-lived credential exists in the extension (the Heed session token). It is Heed-scoped, revocable, never grants Google access, and is treated as sensitive; this is my interpretation of "no refresh tokens in the extension" (Google refresh tokens and anything that can mint Google access). If you read the requirement more strictly, see unresolved #4 for a stricter but worse-UX variant.

### D-05 Gmail synchronization strategy
**Context.** Privacy-first; the mailbox is large; most mail is irrelevant; free quotas; no resident worker.

**Decision.** Server-side **polling with incremental history**: `gmail.readonly`; initial bounded backfill (default 14 days, max 30, cap 300 messages) with the `historyId` captured before listing; then `history.list(messageAdded, labelId=INBOX)` every 15-minute tick plus on-demand sync when the extension opens (at least 2 minutes apart). Headers first (`format=metadata`), body fetched only for messages that pass Stage 1 (hard drops) and Stage 2 (header score at least 1); idempotency through a sync lease and `ProcessedMessage` claim-by-insert (rows only for body-fetched or deferred messages; header-stage drops are counted, not stored); Gmail category labels and bulk headers filter promotions and newsletters before any body fetch. `invalid_grant` leads to `NEEDS_REAUTH`. Expired history (404) leads to a bounded re-backfill. Pause skips the paused window (cursor fast-forward). SENT messages produce completion *suggestions* only.

**Alternatives rejected.** Gmail push (`users.watch` plus Pub/Sub plus webhook plus 7-day watch renewal): near real-time but adds infrastructure, renewal failure modes, and a public webhook; deferred to V2 (D-14). `gmail.metadata` scope (no body access and no `q` search; insufficient to extract tasks). Scraping Gmail's DOM from a content script (fragile, privacy-hostile). Full-mailbox scan on connect (privacy and quota cost, unnecessary). Storing bodies for reprocessing (violates minimization; deferred messages are re-fetched instead).

**Consequences.** Latency is bounded by the 15-minute tick unless the extension is open; the server transiently reads bodies of non-bulk mail that passes header checks (disclosed in PRIVACY). `gmail.readonly` is a restricted scope: fine for 100 or fewer users unverified, and the gating item for growth (D-14).

### D-06 Calendar synchronization strategy
**Decision.** `calendar.events.readonly`; primary calendar only; `events.list` with `singleEvents=true` over `now−1d … now+30d`; **sync tokens** for incremental changes each tick; daily full resync (rolls the window, drops expired events); HTTP 410 leads to full resync. Store minimal fields (title, times, status, HMAC participant hashes and domains) and never the description or attendee emails; descriptions are read transiently for detection. Event moves recompute linked tasks' deadlines and reminders; cancellations flag tasks.

**Alternatives rejected.** `events.watch` channels (webhook plus renewal; deferred). Re-pulling everything each time (wasteful). Storing attendee emails or descriptions (not needed; hashes plus domains suffice for matching). Multi-calendar in V1 (scope and noise; unresolved #6).

**Consequences.** Participant matching uses HMAC hashes, so we can say "the sender is invited" without storing addresses. Recurring-event expansion is delegated to Google (`singleEvents`). Only 30 days ahead is visible, which suits reminder horizons.

### D-07 AI architecture
**Context.** Gemini initially, provider replaceable, cheap, privacy-first, explainable.

**Decision.**
- **Deterministic funnel before AI** (AI.md section 3): hard drops, header scoring with calendar correlation, content cleaning and scoring, injection pattern drop, then minimization and redaction to a 1,500-character excerpt plus at most 5 candidate event titles. Expected to send about 3% of inbox mail to the model.
- **`AiProvider` interface** with a provider-neutral request/result, versioned provider-neutral prompts, typed failures, and a router that adds budget governance, retries, a circuit breaker, and logging. `GeminiProvider` uses structured JSON output at temperature 0; `FakeProvider` powers tests; provenance (`provider`, `model`, `promptVersion`) is stored per evidence row as strings so switching providers needs no migration.
- **Model verifies nothing; code verifies everything:** the quote must be a verbatim substring of the redacted excerpt, dates are validated and cross-checked against chrono, event references must come from the candidate list, titles may not contain URLs, confidence gates decide `OPEN` (at least 0.80), `SUGGESTED` (0.50–0.79), or discard.
- **Budget governor and accounting** *(amended in Stage 0)*: configurable `MAX_AI_REQUESTS_PER_USER_DAY`, `MAX_AI_TOKENS_PER_USER_DAY`, `MAX_EMAILS_ANALYZED_PER_SYNC`, a project-level quota headroom, batching, priority queueing, and quota-aware routing across a **model pool**, all backed by persisted counters (D-23). Quota exhaustion degrades gracefully by queueing; it never disables Heed.
- **Data-use tier guard** *(amended in Stage 0)*: both `free` and `paid` modes are first-class and explicit. Free mode needs `AI_FREE_TIER_ACKNOWLEDGED=true`, the `FREE_TIER` consent variant, and the region attestation; each pool entry declares whether the terms for the configured account allow training (`dataUse`), and a user's data is routed only to entries compatible with the consent that user gave (D-18).
- Models are configuration, never constants. Stage 0 working defaults from secondary sources: `gemini-3.5-flash-lite` primary (reported GA with a free tier), a Flash-class model as secondary; the 2.5 family is reported to retire on 16 October 2026 and must not be targeted. Exact IDs and live quotas are read from the owner's AI Studio project in the Stage 7 spike.

**Alternatives rejected.** Send every email to the LLM (privacy violation, cost, rate limits). Rules-only (cannot resolve "before the interview" or implicit relations; kept as the funnel, not the extractor). On-device model such as Chrome's built-in Gemini Nano (would require email content and tokens inside the extension, violating the secrets constraint; capability also limited). Embedding or classifier models (training data and ops burden without clear gain at this scale). Letting the model schedule reminders or call tools (unbounded behavior and injection risk). (Stage 0 note: "free-tier Gemini is unacceptable for mail content" was the earlier position; the owner's Stage 0 direction is free-tier-first, so it is now handled as a gated, disclosed mode, see D-18 and CF-1.)

**Consequences.** AI cost is $0 in free-tier mode (within quota) and small and capped in paid mode (D-18). The AI boundary is the same in both modes, so moving between them is configuration. English-centric lexicons limit recall (documented).

### D-08 Reminder architecture
**Context.** The product promise is reminders "when it actually matters", with context, quietly.

**Decision** *(amended in Stage 0: server-planned, **server-evaluated**, client-delivered)*. A pure, versioned planner (`policyVersion = 2`) computes deterministic reminder slots from task, event, dependency, and settings state, for five kinds: event briefing (the enriched event reminder, bundling outstanding items, preparations, and dependencies), task deadline, task preparation, task overdue, and dependency blocked; with lead profiles, quiet-hours clamp, snooze handling, detection-urgent slots, and slot keys that make planning idempotent. A `ReminderScheduler` then materializes due reminders through an indexed due-time query, re-checking relevance against live state, composing the final contextual text, and applying caps and coalescing, in one transaction that creates an idempotent `Notification` (D-24). No AI runs at reminder time. Re-planning is triggered by task, event, dependency, settings, and snooze changes through the `REMINDER_PLAN` job. Full rules: ARCHITECTURE section 8.

**Alternatives rejected.** Client-evaluated relevance, caps, and text composition (the original V1 plan; it put business logic in the extension, which the thin-client requirement forbids, and would have to be re-implemented for each future channel). Client-only planning (duplicates logic, harder to test and version). LLM-written reminders (cost, latency, inconsistency, offline failure). One reminder per task (spams when several tasks hang off one event).

**Consequences.** Reminder quality is testable with table-driven and property tests; policy changes ship as `policyVersion` bumps; the engine never scans all tasks or users (due-time index); channels are replaceable. Delivery still depends on the Chrome client being alive in V1 (D-09).

### D-09 Notification architecture
**Decision** *(amended in Stage 0)*. A `NotificationProvider` interface separates "reminder X is due" (engine) from "how it reaches the user" (channel). `ChromeNotificationProvider` is the only V1 implementation, in `PULL_PREFETCH` mode: the server materializes ready-to-show `Notification` rows 36 hours ahead; the extension pulls them through the paged sync feed, schedules a local `chrome.alarm` per notification (rebuilt idempotently after each sync and at browser startup, since alarms may not survive restarts), and displays the payload as-is with `chrome.notifications` and the badge. Actions *Done* and *Snooze 1h* go through the outbox; acks (`DELIVERED`, `CLICKED`, `ACTIONED`) are batched to the server. Quiet hours, caps, coalescing, relevance, and text composition are all **server-side**. Missed notifications (browser closed) produce one catch-up notification on next launch for the last 6 hours (pure presentation); older ones are marked `EXPIRED` by a server sweeper and listed as "Missed". Future `WebPush`, `Email`, and `MobilePush` providers use `PUSH_AT_DUE` (server sends at `deliverAt`) behind the same interface (ARCHITECTURE section 9).

**Alternatives rejected for V1.** Web Push (VAPID) from the service worker (free, but adds subscription storage and push delivery plumbing, and only helps if Chrome is running anyway on most desktops). Email fallback (needs an email provider and adds a new data flow; promising post-beta). Native/desktop or mobile apps (out of scope).

**Consequences.** No notifications while Chrome is closed: clearly disclosed in onboarding; the main product limitation for the beta (unresolved #9), removable later by adding a push channel without touching the engine. A notification can be up to 36 hours stale only in the offline-edit edge case; server-side cancellation through the sync feed handles the online case.

### D-10 Security model
**Decision.** Thin untrusted client, trusted server (SECURITY.md). Google tokens, API keys, client secret, DB credentials, encryption keys exist only server-side (Secret Manager); the extension holds only a revocable Heed session token; CI enforces this with architecture rules and a **forbidden-pattern bundle scan**. Field-level AES-256-GCM encryption (key separate from DB) for refresh tokens and email-derived text; HMAC fingerprints and participant hashes with a separate pepper; every query user-scoped; cross-tenant tests per route; Zod validation; least-privilege IAM with Workload Identity Federation (no long-lived cloud keys); log redaction with canary tests; beta allowlist; kill switch; documented incident runbooks; Limited Use compliance.

**Alternatives rejected.** Plain DB encryption at rest only (a DB leak would expose tokens). Cloud KMS envelope encryption in V1 (better audit and no key in env, but more setup; recommended for V2, see SECURITY section 7). Storing Google tokens in the extension (violates the brief). Row-level security in Postgres (valuable defense in depth, deferred: adds Prisma friction; the route-registry and authz test suite is the V1 control).

**Consequences.** A runtime compromise could decrypt tokens; mitigations are least privilege, small blast radius, and the revoke-all runbook. Accepted residual risks are listed in SECURITY section 16.

### D-11 Free-tier strategy
**Decision.** Every component must have a free tier or near-zero cost, a **hard usage cap or alert**, and a documented degradation path. Stay under about 50% of any free quota at beta scale.

| Component | Free allowance (assumption, see section 2) | Usage at 10 users | Guard |
|---|---|---|---|
| Cloud Run (request-based CPU) | 180k vCPU-s, 360k GiB-s, 2M requests/month (verified) | Well under: ticks plus a few hundred requests/day | `max-instances=2`; billing budget alert $1 |
| Cloud Scheduler | 3 free jobs per billing account (secondary source quoting the official pricing page) | 1 job | |
| Secret Manager | 6 active versions and 10,000 access operations/month per billing account (secondary source quoting the official pricing page) | **One** JSON secret read once per instance start (separate secrets would exceed both limits: about 8 secrets and about 2,900 cold starts a month) | Single runtime secret; rotation adds a version for a short time (pennies if it ever exceeds the free count) |
| Artifact Registry | About 0.5 GB free (to verify) | One slim image | Prune old images |
| Cloud Logging / Monitoring | Free allotments (to verify) | Low volume | 30-day retention |
| Neon Postgres | 100 CU-h, 0.5 GB, 6 h PITR (verified) | About 65 CU-h with 15-min tick; MBs of data | CU-hour alert; tick backoff; Supabase fallback |
| Gemini API (free-tier mode, Stage 0 decision) | Free quota per project and per model; no fixed public table (reported about 500 requests/day Flash-Lite class, about 20/day Flash class; **live value read from the owner's AI Studio project**) | About 3 candidates per user per day, roughly 8–10 requests/day for ten users with batching | Persisted per-user and project-level caps, batching, priority queue, quota-aware pool; data-use caveats in D-18 |
| GitHub Actions | Free minutes (to verify for private repos) | CI plus occasional deploys | Cache; path filters |

| Domain / hosting for privacy page | Not required for the beta (GitHub Pages or API static route) | | Needed only for Google verification (D-14) |

**Expected recurring cost** *(amended in Stage 0)*: **$0** for AI in free-tier mode and $0 for infrastructure while inside the free allowances, plus a one-time $5 Chrome Web Store fee. **Paid dependencies, stated plainly:** Google Cloud requires a **billing account with a card on file** to use Cloud Run and Cloud Scheduler even within the free allowances (unresolved #2); the Web Store fee; and possible sub-cent overages (for example Secret Manager access operations) that the single-secret design avoids. Nothing in the architecture requires paid AI.

**Alternatives rejected.** Render/Fly/Railway free or trial tiers (spin-down or trial expiry, free databases that expire). Cloudflare Workers (generous and card-free, but the free CPU limit of about 10 ms per request cannot run Gmail parsing and detection, and Node compatibility with Prisma is awkward). Vercel Hobby functions (non-commercial terms, short timeouts).

### D-12 Deployment strategy
**Decision.** Single Docker image on **Cloud Run** (min 0, max 2 instances, 512 MiB, 1 vCPU, request-based CPU); **Cloud Scheduler** hits `/internal/tick` every 15 minutes with OIDC; Neon for Postgres; Secret Manager for secrets (one JSON runtime secret, see D-11); Cloud Logging and an uptime check on `/healthz`. Environments: local, CI, staging, prod (staging and prod are separate Cloud Run services, Neon branches, and Google OAuth clients). GitHub Actions deploys through Workload Identity Federation; migrations are expand/contract, applied before traffic shift; smoke test then automatic rollback to the previous revision on failure. Extension released as a CI-built zip; uploaded manually to the Chrome Web Store as **Unlisted** in V1 (pinned `key` builds for load-unpacked fallback). Infrastructure is documented as scripts and a README in `infra/` (Terraform deferred; ten-user scale does not justify it).

**Alternatives rejected.** Always-on VM (free VMs are tiny and insecure to operate). Kubernetes (absurd at this scale). Running the tick inside GitHub Actions cron only (jitter up to many minutes, can be delayed or disabled on inactive repos; kept only as a documented backup trigger).

**Consequences.** Request-based CPU means no work after a response, so on-demand sync is inline with a 20 s budget and the rest waits for the tick. Cold starts are about 1–2 s. *(Stage 0: this is the **current infrastructure** decision: one API, one database, one scheduler-triggered job runner, one extension; every piece sits behind a port so it can be replaced, see D-19, D-20, D-27.)*

### D-13 Data retention strategy
**Decision.** Minimize at ingest, then expire by default: bodies never stored; evidence at most 300 characters (encrypted) lives with its task; completed and dismissed tasks 90 days; events 14 days after end; message log 30 days (written only for messages whose body was fetched or that are deferred); suppressions 365 days; reminders 14 days; tombstones 30 days; audit 90 days; operational logs 30 days; sessions 7 days after expiry; unreviewed suggestions auto-dismiss after 14 days. A daily `RETENTION_PURGE` job enforces the schedule (DATA_MODEL section 8). User-initiated delete is immediate and hard; delete-data and delete-account follow defined cascades and run as the resumable `PURGE_USER_DATA` job (DATA_MODEL section 9). Every table is registered in a typed data inventory that tests tie to retention and deletion (D-26). No custom backups; provider PITR window (6 h) is disclosed. A counts-only `DeletionReceipt` proves erasure without identifiers.

**Alternatives rejected.** Soft-delete everywhere (retains data users asked us to delete). Indefinite retention for analytics (no analytics need in V1). Long audit retention (privacy cost without benefit at this scale).

**Consequences.** Re-detection after purge needs a new inbound message (acceptable). The 30-day message log equals the 30-day maximum backfill window (older messages are excluded by `H_TOO_OLD`).

### D-14 Future scalability strategy *(amended in Stage 0: target is about 1,000,000 registered users)*
**Context.** Today: one to ten users on free tiers. Long-term target: about 1,000,000 registered users **without rewriting the domain model, API contracts, authentication model, integration abstraction, AI abstraction, reminder model, extension architecture, or data ownership model.** The question is where the design bends and where it breaks.

**Decision: scale the boundaries, not the infrastructure.** Build a clean modular monolith with explicit ports (D-19), stateless processes (ARCHITECTURE 4.5), database-enforced idempotency (D-22), indexed due-time scheduling (D-20, D-24), cursor pagination (D-21), and per-user ownership on every row (DATA_MODEL principle 3). Growth then happens by **replacing infrastructure behind those ports**:

| Today | Future (when measured need appears) | What changes | What does not |
|---|---|---|---|
| Cloud Scheduler tick plus `PostgresJobQueue` | Cloud Tasks, Pub/Sub, or SQS worker fleet | A `JobQueue` implementation and the trigger | Handlers, job types, idempotency keys |
| Polling (`nextSyncAt`) | Gmail `users.watch` plus Pub/Sub and `events.watch` push; polling as repair | `IntegrationProvider` capability and an ingestion endpoint | Detection, domain, API |
| `ChromeNotificationProvider` only | Web push, email, mobile push providers | New `NotificationProvider` implementations | Reminder planner, scheduler, composer |
| Free-tier Gemini via the pool | Paid Gemini, other providers, batch APIs, distilled models | `AI_MODEL_POOL` entries and adapters | `AiProvider` contract, validators, prompts' schema |
| Single Neon Postgres | Larger Postgres, pooling, read replicas for read-heavy endpoints, time partitioning of large tables, then hash partitioning by `userId` if proven necessary | Infrastructure, migrations, partition DDL | Module repositories' interfaces, API |
| One API service | Several stateless API instances behind a load balancer | Deployment settings | Code (already stateless) |
| Postgres rate limiter | Redis or an edge limiter | A `RateLimiter` implementation | Callers |

Capacity variables, per-stage bottlenecks (1, 5–10, 100, 10,000, 100,000, 1,000,000 users), and the detailed migration path are in **SCALE_MODEL.md**. Nothing in that path is built now (rule: no Kubernetes, no microservices, no Kafka, no Redis, no Elasticsearch without a current need and a documented migration path).

**Compliance gate (the real limit):** Google OAuth verification including the annual third-party security assessment (CASA) for the restricted Gmail scope is required before more than 100 users; reported self-serve cost is roughly $540–$1,000 per year plus weeks of lead time (secondary sources). Free-tier AI mode must end before any verification submission (D-18). At large scale additional Gmail/Calendar API quota would have to be requested from Google (the Gmail per-project limits reported by secondary sources are 1.2 million quota units per minute and 6,000 per user per minute; the reported per-method costs conflict between sources and must be read from the official page before capacity planning).

**What already scales:** stateless API, user-scoped data model with per-user change sequence, idempotent jobs with leases, provider ports, deterministic planner and scheduler, versioned rules/prompts/policies, eval harness.

**Known limits (documented, not hidden):** per-user serialization on `changeSeq` (fine for any realistic per-user write rate), polling-based sync (replaced by push), free-tier quotas, single region, single operator, and the compliance gate above.

### D-15 Repository and tooling
Monorepo with pnpm workspaces; packages `shared`, `detection`, `ai`, `eval`, `config`; apps `extension` and `api`; enforced dependency boundaries (eslint plus dependency-cruiser). TypeScript strict with project references; ESLint and Prettier; Vitest everywhere; Node version pinned in `.nvmrc`. Turborepo and Nx deferred (pnpm scripts and CI caching suffice).

### D-16 Testing approach
Layered tests with deterministic clocks and no real network in CI: unit and property tests for pure logic, a synthetic detection corpus with stage-level metrics gating CI, contract tests for AI providers, integration tests against Postgres with a fake Google server, a mandatory authz suite, privacy-invariant tests (no bodies stored, no content in logs, ciphertext at rest), extension component and worker tests, Playwright E2E with the real extension loaded in Chromium, a built-bundle secret scan, and coverage thresholds (details: ARCHITECTURE section 14). Real Gemini is only used in an optional, manually triggered eval workflow.

### D-17 Time handling
All instants are stored as UTC `timestamptz`; user-facing and deadline semantics use the user's IANA timezone (Luxon on the server, `Intl` in the extension). Date-only deadlines (`DueGranularity.DAY`) resolve to end of day local time and drive day-based reminder slots. The planner and chrono parsing receive an injected clock and timezone, and DST edge cases are covered in the corpus and planner tests.

### D-18 Free-tier AI strategy *(Stage 0; resolves earlier unresolved #1 by owner direction, with gated residual risk)*
**Context.** Stage 0 requires: the complete V1 intelligence for one user and for 5–10 beta users using **free-tier AI only**, no paid AI dependency, and no feature reduction. Verified (secondary sources only: the official Gemini pages could not be fetched from the build environment, which blocks `ai.google.dev`; see section 2): there is no fixed public free-quota table any more and the live per-project, per-model quota is shown in AI Studio; reported figures are about 500 requests/day for Flash-Lite-class models and about 20/day for Flash-class models; Pro-class models were reported removed from the free tier in April 2026; free quotas apply **per project, per model**. Under the provider's terms for unpaid services, submitted content may be used to improve Google's products and may be read by human reviewers; the same terms (as summarized) say that only paid services may be used when an app is made available to users in the EEA, Switzerland, or the UK; and Google's Workspace API user-data policy (as summarized) prohibits using Google user data to train or improve AI/ML models. A no-training free alternative exists in principle (Cloudflare Workers AI states in its documentation that customer content is not used to train models and offers a free daily allowance), but quality for this task is unmeasured.

**Decision.** Free-tier mode is a first-class, explicit operating mode. Capacity is solved by engineering, never by removing capability:
1. **Candidate reduction:** deterministic funnel, about 3 AI candidates per user per day (about 2.25 inbox, 0.5 sent, 0.25 calendar description).
2. **No repeated work:** `AiAnalysis` partial-unique index (a source is analyzed once per prompt/rules version); unchanged calendar descriptions skipped by `etag`; thread-aware dedupe.
3. **Batching:** up to 4 same-user items per request when at least 3 are waiting. Requests per day, the binding free-tier dimension, drop by about 4x at similar token cost.
4. **Priority queue and backpressure:** deferred candidates are drained by priority (event participant, event within 48 h, deadline phrase, newest); backfill is bounded (300 messages, `MAX_EMAILS_ANALYZED_PER_SYNC`) and never starves live mail; it may take days to drain on a 20-requests/day model, which delays only *older* mail.
5. **Quota-aware model pool:** per-model free quotas add up; routing uses persisted `AiProviderUsage` and `blockedUntil`, so all instances agree.
6. **Compact prompts, usage accounting, retries with backoff, circuit breaker** (AI.md).
Capacity check: one user needs about 3 requests/day (about 1–3 batched); ten users about 30 candidates/day, about 8–12 batched requests/day, plus a one-time backfill of about 420 candidates (about 105 batched requests, one day on a 500/day model, several days on a 20/day model). Even the pessimistic 20/day quota sustains one user and, with batching and priority, five to ten users' steady state; the Stage 7 spike replaces these estimates with the owner's live quota.
**Guardrails for free-tier mode:** (a) `AI_FREE_TIER_ACKNOWLEDGED=true` is required or the server refuses to enable Gmail processing; (b) each user gets the plain-language `FREE_TIER` disclosure and must consent, recorded with the variant; declining means no AI analysis for that user (calendar features still work); (c) each user attests they are **not** in the EEA, Switzerland, or the UK, and AI analysis is refused without it; (d) **per-user data-use routing:** a pool entry has `dataUse = NO_TRAINING | MAY_TRAIN`; a user who has not consented to `MAY_TRAIN` is only routed to `NO_TRAINING` entries, so adding a no-training free provider to the pool (Stage 7 spike, optional, owner approval needed because it adds a second data processor) lets users who decline the Gemini free-tier terms keep full functionality; (e) minimization and redaction exactly as in paid mode.
**Exit criteria (mandatory):** free-tier mode must be switched off (pool entries on a no-training tier, consent variant `PAID_TIER` or equivalent) **before any Google OAuth verification submission, any public listing, or any user in a restricted region.** The switch is configuration plus a consent re-prompt (`CONSENT_VARIANT_STALE`).

**Alternatives rejected.** Paid tier now (contradicts the brief; remains the one-line switch). Disabling AI for free-tier users or running "lite" features (violates parity). A local or self-hosted model (no free host has the compute). Routing everything through one Flash-Lite model without batching or priority (fragile against quota changes).

**Consequences / risks (stated plainly).** (1) Policy tension with Google's Limited Use and user-data policies for Gmail content when the free tier may train on it; acceptable only as a closed, consented beta, and it blocks verification until removed (CF-1). (2) Region gating can exclude users. (3) Quotas have already changed several times in 2025–2026 and can change again without notice; the design degrades (delays new analysis) instead of failing. (4) The paid-tier alternative is only a configuration change.

### D-19 Provider and module boundaries (the genuine external ports) *(Stage 0; complements D-02 and D-07)*
**Decision.** Domain logic depends only on these ports: `IntegrationProvider` (`GmailProvider`, `CalendarProvider`, future Outlook), `AiProvider` (`GeminiProvider`, `FakeProvider`, future providers; D-07), `NotificationProvider` (`ChromeNotificationProvider`, future web push/email/mobile; D-24), `JobQueue` (D-20), `RateLimiter`, `SecretsProvider`, and `Clock`; the database is reached only through each module's repository over Prisma and plain PostgreSQL features. The modular monolith has explicit modules for authentication, users, integrations, Gmail, Calendar, synchronization, detection, AI, tasks, events, commitments, dependencies, evidence, reminder planning, notification delivery, usage accounting, privacy, audit, and jobs (ARCHITECTURE 4.2), each owning its tables and exposing a typed service interface; Prisma types never cross a module boundary. **Alternatives rejected:** abstracting everything (logging, HTTP framework, validators; unneeded cost), microservices per module (premature), a shared "god" data layer (couples modules, blocks partitioning later). **Consequences:** a vendor or infrastructure change touches an adapter and configuration; the "outbound email provider" is the future `EMAIL` channel of `NotificationProvider`, not a separate abstraction.

### D-20 Job processing abstraction *(Stage 0; amends the job section of D-02/D-12)*
**Decision.** A `JobQueue` port (`enqueue` idempotent, `claim`, `heartbeat`, `complete`, `fail`, `cancel`) and queue-agnostic `JobHandler`s registered by modules. V1 implements it as `PostgresJobQueue` (leases plus `FOR UPDATE SKIP LOCKED`) driven by one Cloud Scheduler tick; **no `setInterval` or process timers anywhere**. Every job has id, type, status, attempts, createdAt, scheduledAt, startedAt, completedAt, error (sanitized), and a required idempotency key, plus queue, priority, correlation id, and lease. The tick runs **due-time queries** (`Integration.nextSyncAt`, `Reminder.triggerAt`, deferred-AI priority, `Job.scheduledAt`), never loops over users. A later `CloudTasksJobQueue`/SQS/Pub/Sub implementation enqueues by creating a task that calls an authenticated runner endpoint and reuses the same handlers. **Alternatives rejected:** in-process timers and `setInterval` (die with scale-to-zero, break with multiple instances), pg-boss (reasonable later; adds its own schema and API surface now), BullMQ/Redis (new infrastructure without current need), GitHub Actions cron as primary (jitter, may be disabled; kept as a backup trigger). **Consequences:** latency is bounded by the 15-minute tick except for on-demand sync and pre-materialized notifications; accepted.

### D-21 Pagination strategy *(Stage 0; amends API.md)*
**Decision.** Every list endpoint is cursor-paginated with opaque, HMAC-signed keyset cursors over a fixed sort key plus id, a default and maximum `limit`, and a user-prefixed supporting index; **no OFFSET and no unbounded collection responses**. This includes tasks, events, reminders, notifications, sessions, sender rules, and the extension sync feed (which pages by change sequence with `hasMore`). Export streams NDJSON by keyset-paging each table (async job with a signed link at larger scale). **Alternatives rejected:** OFFSET/limit (degrades linearly and is inconsistent under writes), page numbers, returning full collections. **Consequences:** clients must loop on `nextCursor`/`hasMore`; sort orders are part of the contract.

### D-22 Idempotency *(Stage 0)*
**Decision.** Every external synchronization and every effect with a retry path is idempotent by a **database constraint**, not only application checks; the full map is DATA_MODEL section 5: integration sync leases, `ProcessedMessage` claim-by-insert, `Event` provider-id unique, `Task` fingerprint and `Evidence` unique, `AiAnalysis` partial unique on success, `Reminder (userId, slotKey)`, `Notification.idempotencyKey`, `Job.idempotencyKey`, `ApiIdempotencyKey (userId, key)` for API retries, and resumable purge jobs. Tests run each pipeline twice and concurrently and assert no duplicate rows, tasks, reminders, or notifications. **Alternatives rejected:** application-level "exists?" checks (race conditions), exactly-once queues (not available on the chosen stack). **Consequences:** a few extra unique indexes; a retry can never double-notify where the provider supports idempotency keys, and the Chrome channel is de-duplicated by notification id.

### D-23 Usage accounting *(Stage 0)*
**Decision.** Provider-neutral accounting in the database: `AiUsage` per user, day, provider, model, and operation (requests by outcome, candidates analyzed, estimated tokens), `AiProviderUsage` per provider, model, and day (project-level quota and a persisted `blockedUntil` after a 429), and `AiAnalysis` per analyzed item (no content). Limits are configuration (`MAX_AI_REQUESTS_PER_USER_DAY`, `MAX_AI_TOKENS_PER_USER_DAY`, `MAX_EMAILS_ANALYZED_PER_SYNC`, `AI_GLOBAL_REQUESTS_PER_DAY`, batching and deferral settings, with single-user and beta defaults), and each pool entry carries its own `ModelQuotaPolicy` as data, so the domain never encodes any vendor's quota system. Token counts are estimates (character-based, corrected from provider usage metadata when available). **Alternatives rejected:** relying on vendor quota APIs or dashboards (not portable, not per user), in-memory counters (lost on restart, wrong across instances). **Consequences:** a small write per request, acceptable at AI-request volumes; the same tables drive the user-visible "analysis delayed" status and cost reporting later.

### D-24 Thin extension and server-composed notifications *(Stage 0; amends D-08, D-09, D-01)*
**Decision.** The extension is presentation, cache, session state, and Chrome integration only. The server runs relevance, quiet hours, caps, coalescing, and **composes the final notification text** (title, body, actions, in-extension deep link) in a pure `NotificationComposer`; the extension receives ready-to-show payloads (36-hour lookahead), schedules alarms, displays, and acks. Reminders are plans (`Reminder.triggerAt`); notifications are deliveries (`Notification`, one per reminder, channel, and payload generation). The reminder engine never references Chrome. **Alternatives rejected:** shared client-side predicates and templates (business logic in the extension, re-implemented per channel). **Consequences:** more server logic (good for testing and for future channels); bounded staleness for pre-fetched payloads (cancelled through the sync feed).

### D-25 Expanded domain model for the full V1 intelligence *(Stage 0)*
**Context.** The brief requires detecting meetings, appointments, deadlines, explicit tasks, commitments, and dependencies, with context about people, organizations, related email, related events, and personalization; the original model had calendar-mirror events, tasks with one anchor, and no commitments, people, or personalization.
**Decision.** (1) `Task` gains `kind` (action, preparation, deadline, commitment) and `direction` (requested of user, promised by user, self); (2) a first-class `Dependency` table (task→event with before/after/during, task→task blocked-by) replaces the single anchor and drives effective deadlines; (3) `Counterparty` (encrypted name and organization, hashed email, domain) provides "the recruiter at Acme" context and is garbage-collected when unreferenced; (4) `Event` unifies calendar-synced, **email-detected**, and manual events (detected events are suggestions, merged with a matching calendar event, and Heed never writes to Google Calendar); (5) sent-mail commitments are detected only under a separate opt-in consent; (6) deterministic personalization through `SenderStats`, per-event `remindMode`, lead profiles, and sender rules. **Alternatives rejected:** keeping a single anchor column (cannot express task-task dependencies), free-text relationship fields (not queryable), an ML personalization model (opaque, costly). **Consequences:** a larger schema and prompt (AI `extract-v2`), more consent surface, and more explainability work, all required for parity.

### D-26 Data inventory registry (privacy by construction) *(Stage 0)*
**Decision.** A typed registry in `packages/shared` lists every table and sensitive column group with purpose, consent basis, storage and encryption tier, retention, accessors, and deletion path; CI fails if a model is missing, if retention disagrees with the purge configuration, or if the delete-data test leaves rows; the "what Heed stores" page and the export are generated from it. This is how the system "knows exactly what data is collected, why, where it is stored, how long it is kept, who can access it, and how it is deleted." **Alternatives rejected:** prose-only documentation (drifts). **Consequences:** every schema change must update the registry (a feature, not a cost).

### D-27 Scale hot-spot corrections from the Stage 0 review *(Stage 0)*
**Decision.** The review of the original design against the 1M-user target changed: (1) the tick scans due-time indexes instead of all users (`Integration.nextSyncAt`); (2) rows are not written for header-stage drops (`ProcessedMessage` only for body-fetched or deferred messages, retention 30 days) and `SyncRun` is written only when work or an error occurred, because per-poll logging would produce billions of rows at scale; (3) rate limiting is database-backed behind a port instead of per-instance memory; (4) the sync feed, export, and all lists are paged; (5) per-user deletion is a resumable batched job; (6) `Reminder (triggerAt, priority) WHERE status = 'PENDING'` makes due-reminder scans independent of total task count; (7) polling is explicitly a V1 choice with push as the planned replacement. **Consequences:** none of these changes the domain API; all are cheap now and expensive to retrofit later.
