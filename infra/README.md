# Heed infrastructure (staging foundation)

Nothing here is provisioned automatically. These files describe the **smallest reasonable staging
configuration** that follows docs/ARCHITECTURE.md section 12 and docs/DECISIONS.md D-11/D-12, and the scripts
a human runs once.

| File                            | Purpose                                                                                                                                                    |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Dockerfile`                    | Production API image: distroless Node 24, non-root (65532), base images pinned by digest, no secrets                                                       |
| `cloudrun/service.staging.yaml` | Cloud Run service: min 0 / max 2 instances, 1 vCPU, 512 MiB, request-based CPU, runtime secret injected                                                    |
| `scripts/bootstrap-staging.sh`  | One-time, idempotent: APIs, Artifact Registry, 3 service accounts, the single runtime secret, least-privilege IAM, Workload Identity Federation for GitHub |
| `scripts/create-tick-job.sh`    | Cloud Scheduler job -> `POST /internal/tick` with an OIDC token (1 of the 3 free jobs)                                                                     |

## One-time setup (human, requires a GCP project with a billing account)

1. `PROJECT_ID=... REGION=... GITHUB_REPO=owner/repo bash infra/scripts/bootstrap-staging.sh`
2. Set the printed values as GitHub **environment variables** on an environment named `staging`
   (variables, not secrets: nothing in GitHub holds a credential; deploys use Workload Identity Federation).
3. Run the `Deploy API (staging)` workflow (manual). It builds the image, pushes it, applies the service
   YAML, and smoke-tests `/healthz` and `/readyz` over HTTPS.
4. `PROJECT_ID=... REGION=... SERVICE_URL=https://... bash infra/scripts/create-tick-job.sh`
5. Create a billing budget alert (suggested: 1 USD) in the console.

## What is deliberately NOT here

No Redis, Kafka, Elasticsearch, Kubernetes, managed queue, or paid observability platform (DECISIONS D-11,
D-27). No database yet (Stage 2). No production environment yet (Stage 16). No long-lived cloud keys.

## Secrets

All runtime secrets are **one JSON document** in Secret Manager (`heed-runtime-config`), injected into the
container by Cloud Run at instance start as `HEED_RUNTIME_SECRETS_JSON` and validated at boot by
`@heed/config`. Stage 1 requires only the data keys and HMAC pepper (random values generated by the bootstrap
script and never printed). Later stages add the database URL, Google client secret, and Gemini key as new
versions of the same secret. Rotation = add a version, redeploy.

## Known caveat: `/healthz` on Cloud Run

Cloud Run's front end has been reported to reserve some paths. The container's own probes reach `/healthz`
directly, but verify external reachability of `GET /healthz` and `GET /readyz` on the first deploy; if a path is
intercepted, record it in docs/DECISIONS.md and add an alias rather than changing the documented contract
silently.

## Teardown

`gcloud run services delete heed-api-staging`, `gcloud scheduler jobs delete heed-tick-staging`,
`gcloud secrets delete heed-runtime-config`, `gcloud artifacts repositories delete heed`, and delete the three
service accounts and the workload identity pool.
